02 · GIT — MAIN / DEVELOP / FEATURE
그래도 나눈다면, 역할부터 분명하게
main
최종 제출 · 배포 가능한 stable 버전
develop
개발 중인 기능을 모으는 통합 브랜치
feature/*
기능 단위 작업 브랜치
초기 환경 세팅도 develop에서 다듬은 뒤 main으로. main에는 검증된 상태만 들어갑니다.
develop → main merge 전 체크리스트
이번 배포 범위가 명확하다
develop의 기능이 모두 완료됐다
코드 리뷰가 끝났다
불필요한 커밋이 정리됐다
테스트가 통과한다
지금 제출·배포해도 되는 상태다
하나라도 ‘아니오’면 merge하지 않는다

02 · GIT — REPOSITORY
레포 구조도 ‘왜’가 있어야 한다
모노레포
project/ ├─ frontend/ ├─ backend/ └─ ml/
장점 한 PR로 프론트·백엔드를 함께 바꾸고, 버전을 맞추기 쉽다
명확해야 할 것 폴더 구조, 패키지·의존성 관리, 폴더별 배포·CI 범위
레포 분리
project-frontend/ project-backend/ project-ml/  
장점 레포마다 책임·권한·배포가 독립적이다
명확해야 할 것 각 레포의 책임, 연동 방식(API 명세·버전), 공통 코드 위치
정답은 없습니다. “우리 상황에선 이게 가장 단순하고 안정적이다”라고 합의했다면 충분합니다. 다만 느슨한 운영과 기준 없는 운영은 다릅니다.

02 · GIT — SUMMARY
정리: Git 전략을 정할 때 6가지 원칙
1
main은 안정적인 버전으로
언제 받아 실행해도 돌아가는 상태를 유지
2
작업은 기능 단위 브랜치에서
브랜치 하나 = 목적 하나, 끝나면 삭제
3
PR · merge 기준은 팀이 합의
리뷰어, 승인 수, merge 방식, main 진입 조건
4
커밋은 추적 가능한 단위로
‘수정’, ‘asdf’ 같은 커밋이 쌓이면 추적이 어렵다. 의미 단위로 남기고 잔커밋은 squash로 정리
5
전략은 팀에 맞게
코드 구조, 협업 방식, 팀의 숙련도에 맞춰 고른다
6
복잡함보다 설명 가능함
멋있어 보이는 전략보다 이유를 말할 수 있는 전략

03 · W&B — SWEEPS
Sweeps: 하이퍼파라미터 탐색을 자동으로
1
sweep.yaml에 탐색 범위와 목표 지표를 정의
2
wandb sweep으로 등록하면 sweep ID가 발급
3
wandb agent가 조합을 받아 train.py를 반복 실행 — 여러 GPU·PC에서 동시에 돌릴 수 있음
4
대시보드의 parameter importance, parallel coordinates 차트로 비교
train.py 안에서는 wandb.init() 후 run.config["lr"]처럼 값을 읽습니다.
# sweep.yaml program: train.py method: bayes            # grid | random | bayes metric: {name: val/mAP50, goal: maximize} parameters:   lr: {min: 0.0001, max: 0.01}   batch_size: {values: [16, 32, 64]} # 터미널 wandb sweep sweep.yaml       # → sweep ID 출력 wandb agent my-team/defect-detect/<sweep_id>

03 · W&B — ARTIFACTS
Artifacts: 파일에도 버전과 계보를
defect-data:v3
데이터셋 artifact
run: train-yolov8n
이 데이터를 쓴 학습 run
detector:v7
그 run이 만든 모델 artifact
어떤 데이터로 어떤 모델이 나왔는지 그래프로 추적합니다. 내용이 같으면 새 버전을 만들지 않습니다.
# 데이터셋 올리기 art = wandb.Artifact("defect-data", type="dataset") art.add_dir("data/defect-detect-3") run.log_artifact(art)      # → defect-data:v0, v1, ... # 다른 run에서 가져다 쓰기 data_dir = run.use_artifact("defect-data:latest").download() # 학습한 모델 올리기 model_art = wandb.Artifact("detector", type="model") model_art.add_file("runs/best.pt") run.log_artifact(model_art)

04 · MLFLOW — WHAT IS
ML 라이프사이클을 관리하는 오픈소스 플랫폼
직접 서버를 띄우거나 로컬에 기록하는 오픈소스입니다. 기록이 우리 쪽 저장소에 남고, Databricks 같은 관리형 서비스로도 쓸 수 있습니다.
Tracking
파라미터·지표·파일(artifact)을 run 단위로 기록하고 UI에서 비교
Models
프레임워크가 달라도 같은 형식으로 저장 — 불러오면 predict() 하나로
Model Registry
모델 버전 관리, alias(@champion)로 ‘지금 쓰는 모델’ 지정
GenAI (MLflow 3)
LLM·에이전트 Tracing, 평가, Prompt Registry

04 · MLFLOW — HOW TO USE
서버 띄우고 run 기록하기
터미널
pip install mlflow mlflow server --host 127.0.0.1 --port 5000 # → http://127.0.0.1:5000 에서 UI 확인
한 줄로 자동 기록
mlflow.autolog()
PyTorch Lightning · Keras · scikit-learn · XGBoost 등 지원 프레임워크는 파라미터·지표·모델을 자동으로 남깁니다.
MLflow 3 log_model에 artifact_path 대신 name을 씁니다. 모델이 run과 별개인 ‘LoggedModel’로 관리됩니다.
import mlflow mlflow.set_tracking_uri("http://127.0.0.1:5000") mlflow.set_experiment("defect-detect") with mlflow.start_run(run_name="yolov8n-lr1e-3"):     mlflow.log_params({"lr": 1e-3, "epochs": 50,                        "dataset": "defect-detect/3"})     for epoch in range(50):         loss, map50 = train_one_epoch(...)         mlflow.log_metric("val_mAP50", map50, step=epoch)     mlflow.pytorch.log_model(model, name="model")

04 · MLFLOW — MODEL REGISTRY
Model Registry: 버전과 alias로 관리
run
학습 1회 · params, metrics
LoggedModel
run에서 저장한 모델
defect-detector
등록된 모델 · v1 · v2 · v3
@champion
alias가 가리키는 버전 = 운영 모델
# 기록하면서 바로 등록 (버전 번호 자동 증가) mlflow.pytorch.log_model(model, name="model", registered_model_name="defect-detector") # 운영 모델 지정: 버전 번호 대신 alias (예전 Staging/Production stage를 대체) from mlflow import MlflowClient MlflowClient().set_registered_model_alias("defect-detector", "champion", 3) # 쓰는 쪽은 alias로 불러오기 → 모델을 바꿔도 코드는 그대로 model = mlflow.pyfunc.load_model("models:/defect-detector@champion")
